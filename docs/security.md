# Security model and first-release boundaries

The [31 October 2026 security assessment](security-assessment-2026-10-31.md) records twelve confirmed application findings with code remediations and passing scoped regressions. Upstream/container vulnerabilities and native deployment acceptance remain open. That report is a finite assessment, not VA clearance or production certification.

## Controller and browser trust

The controller controls intended access across the fleet and belongs on a protected management network. Keep its endpoint issuing CA/key private. Endpoint routes use enrolled client certificates. Browser access supports single-tenant Microsoft Entra ID OpenID Connect sign-in, with application-owned access records and exactly three roles: `read_only`, `admin`, and `super_admin`.

Entra establishes identity through the configured tenant's `tid` and user's immutable `oid`. Only an enabled Prṛthak access record grants access. Email, display name, directory groups and token app-role claims never grant or promote a role. A Super Admin alone can create any application user, assign any of the three roles, change/disable/reactivate users and revoke sessions. Admin and Read Only cannot create any user or promote themselves. Admin and Super Admin manage infrastructure; Read Only is view-only. The last enabled Super Admin is protected, and a Super Admin cannot change their own role or disable themselves.

The authorization-code flow uses PKCE S256, single-use state, nonce, browser binding, tenant/issuer/audience/time checks and RS256/JWKS signature verification. The client secret stays on the controller. Local eight-hour sessions are stored as hashes and sent in Secure, HttpOnly, SameSite=Lax cookies. Session mutations require CSRF protection and same-origin validation. Shared bearer tokens are ignored when Entra is configured. Legacy local-token mode remains a lab compatibility path when Entra is absent; it is not the organizational deployment model.

Audit records for Entra sessions identify the tenant/object identity. Disabling an application user or changing its role revokes local sessions immediately; requests also re-check enabled status and role in the shared database. Entra-side disablement or Conditional Access changes are evaluated at the next sign-in, not continuously during an existing local session. There is no CAE integration. Sign out ends the local Prṛthak session, not the user's Microsoft session. See [Entra configuration](authentication.md).

Implementation and signed-token tests do not establish that an organization's live tenant, MFA, DNS, certificates, redirect, proxy policy or failover is correctly configured. Real-tenant acceptance remains necessary. Endpoint/internal-leaf lifecycle, authorized Admin changes, assignment/package signatures, reviewed external notifications and supervised recovery are implemented with isolated evidence. Full target Linux/failure, live tenant/provider and physical WAN/native DB-fencing acceptance remain required. Complete compromised-CA recovery is a separate fenced offline operation. The 20-server pilot has not started.

## Endpoint trust

The agent verifies controller TLS during enrollment; there is no insecure-skip-verify switch. It persists its local key and CSR before requesting enrollment. Client certificate identity, rather than a server ID in a report, determines which endpoint can report, pull policy or upload events. A 15-minute single-use token authorizes one endpoint identity; an identical CSR/hostname retry within expiry recovers the original certificate after response loss. A changed request cannot reuse it. The client leaf lasts 90 days; authenticated renewal begins in the 30-day window with tracked 24-hour overlap and exact registry revocation. A one-time recovery token is a separate 15-minute credential, not implicit revocation of the old identity. HTTPS server trust (`ca_cert`), optional separate endpoint issuer trust (`endpoint_ca_cert`) and Ed25519 assignment trust are independently pinned; renewal/recovery never accepts replacement roots from its response.

Enrollment establishes identity only. Tokens and agent configuration do not supply business tags or DC/location; new token requests reject nonempty metadata and legacy defaults are ignored. A planned reservation may bind a token to an exact hostname; planned addresses are unverified and do not enter policy-source membership. An authenticated report creates live inventory. Reports cannot override business tags or location.

The endpoint runs privileged commands only locally and communicates outbound. It has no listening control port and never executes controller-supplied shell commands. Policy data is validated and passed as individual process arguments. Local root and other privileged firewall managers can still change rules. Authentication does not make telemetry or reported IP ownership tamper-proof.

## Temporary learning

Learning is assigned by endpoint, port/protocol and expiry. The endpoint persists ownership and expiry locally. Current typed collection uses bounded native conntrack observations and verified NFLOG denial taps, with explicit separate units and coverage. Legacy journal scopes stay labelled historical. Collection adds no ACCEPT action; cleanup removes only owned observation instrumentation. Interrupted or sampled collection must report incomplete coverage; observations are attempts, not proven application success. Learning expiry never removes access policy.

Queued events retain session ID and event time. Ingest validates assignment, ports, time windows, bounds and idempotent batch identity. Delayed uploads have a short post-expiry grace but event timestamps must remain in the collection window. Traffic payloads are not collected. Observe-and-recommend never grants access. Explicit auto-allow requires local opt-ins, fresh frozen per-host scope and the initiating authorized Admin session action; only eligible exact source/service hits inside that active authority can create a separate additive overlay. SSH/controller protection and endpoint transaction checks remain mandatory.

## Firewall rollout

Preview is the default. Compiled policy, approved rollout, agent acknowledgement and observed effective firewalld state are distinct. The managed adapter installs source accepts and per-port rejects at reviewed priorities, refuses conflicting contexts, protects actual SSH ports with pinned management CIDRs and requires fresh mTLS/SSH-banner health. It journals exact writes and arms an independent systemd rollback service. The small adapter retains 64 rich rules; capable 0.6 agents use bounded pre-provisioned source banks for larger managed/learned sets. Missing or externally referenced banks block mutation. Unsupported contexts fail before mutation.

A live authorized Entra Admin's Save/Apply publishes exact policy intent directly. The same authenticated actor remains bound to any immutable review; there is no second-person or pilot-mode requirement. Deny/restrictive imported changes and restrictive learned edits/removal retain two explicit same-actor confirmations. Destructive database recovery remains Super Admin-only and requires two explicit confirmations by that same Super Admin. Local endpoint opt-ins, signed scope, current role/session checks, management protection and rollback remain mandatory. Changed snapshots invalidate their exact review; failed transactions remain held. Application history is append-only through the API, not tamper-proof against a database administrator or compromised controller. See [managed enforcement](managed-enforcement.md).

Business metadata is centrally managed by Admin or Super Admin. A server has one saved location and multiple custom tags. Per-field precedence is manual override, exact-IP CSV profile, subnet location, then unassigned. Subnets supply location only. Manual removal and explicit Unassigned remain pinned until reset. Unknown DC tags do not create locations; discovered process names do not create business application tags.

Bulk/CSV/subnet/profile-removal plans need before/after review and separate nonce-bound apply. Relevant state changes invalidate review. These affect membership and intended bundles; firewall writes still need current exact Admin authority and endpoint protections. Conflicting mappings remain visible. Only authenticated agent payloads supply live inventory IPs; peers/forwarded headers/manual PATCH cannot replace them. Longest prefix resolves overlapping subnet rules; exact normalized CIDRs are unique. Duplicate IPs cannot classify endpoints into different DCs, and ambiguous exact-IP CSV bindings are withheld. Reported address ownership itself is still an endpoint claim rather than cryptographic packet identity.

UFW is detected, not silently disabled. Migration to firewalld is a separate reviewed operation. The validated Ubuntu lab does not certify all RHEL/Ubuntu, SELinux/polkit or IPv6 configurations. Test actual management paths, reload/reboot and rollback before enforcement. Retirement requires verified managed-access/collector cleanup; it rejects the old identity but does not uninstall the service or erase firewall rules.

## Independent signatures, notification delivery and recovery

Ed25519 assignment envelopes bind the deployment, endpoint, exact services/sources, versions, protection/approval, learning and polling intent. Invalid/foreign/expired replacements block mutation while committed rules persist. Public trust is independently pinned. The optional offline provider has exact independently signed artifacts and public trust only; an online signing seed accessible to a compromised controller process does not isolate that authority. Verify separately signed release archives before extraction. See [signing operations](policy-signing.md).

Notifications default off. Super Admin reviews exact resolved destinations/recipients before enabling Slack, HTTPS webhook or TLS/STARTTLS SMTP. Shared purpose-bound encryption seals configuration; missing/foreign key material fails closed. DNS pinning/review, strict TLS, no redirects and restricted private-network approvals constrain delivery. Durable per-occurrence IDs prevent acknowledgement floods and allow a later outage/recovery. Provider acknowledgement is not inbox proof. Unknown Slack/SMTP sends are held for duplicate-aware review; generic webhook automatic retries after ambiguity require an explicit receiver idempotency guarantee.

Supervised GUI recovery requires a verified local database archive plus the current matching PKI/Vault/live safety ledger and one current Entra Super Admin completing the explicit same-actor confirmations. It drains/fences writers, checks candidates/readiness, retains original databases/protected rollback material and invalidates sessions/unused credentials/pending plans/automatic learning before release. Current revocations, disabled users, retired identities and immutable history survive. Missing trusted live context blocks online recovery; archive-only offline DR and compromised-CA recovery require a separately controlled procedure. Queueing is not successful restore. See [0.6 evidence limits](release-0.6.md).

## Local development

Demo mode is loopback-only, unauthenticated and explicitly synthetic. It never contacts real endpoints or changes firewall rules. Keep generated keys, tokens, sessions and databases in ignored private directories. Never commit populated secrets. Cross-compilation and simulation do not prove Linux enforcement.

Source-bank preparation is a separate explicit GUI maintenance action; it can perform a controlled reload only after supported runtime/permanent parity, fresh management checks and watchdog setup. It never grants access or enables enforcement. See [source-set preparation](source-bank-preparation.md).
