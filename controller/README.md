# Prṛthak · पृथक् controller development baseline

The 0.6 controller uses Python 3.10+, local SQLite or shared PostgreSQL, and the controller requirements. The installed serving path is bounded Gunicorn HTTPS; the explicit development backend is for fixtures. Install `controller/requirements.txt` even when starting a fresh CLI runtime. OpenSSL supports development CA issuance. Run commands from the repository root. The appliance image supplies its pinned runtime/dependencies.

## Local synthetic dashboard

The dashboard supports direct GET/refresh URLs at `/overview`, `/servers`, `/policies`, `/traffic`, `/alerts`, and `/activity`. These serve the UI shell; data APIs still require authentication outside demo mode. Unrecognized routes and path traversal remain 404.

```sh
python3 -m controller --demo --listen 127.0.0.1:8787 --data-dir .local/demo
```

Demo mode binds to loopback only, bypasses authentication, and seeds an explicitly synthetic 14-host fleet only when its data directory is empty. It never contacts or modifies real endpoints. An explicit synthetic demo ticker refreshes only the known seeded host scenarios every 30 seconds, preserving one offline host and one policy-error host. It simulates policy acknowledgements and collector state for those hosts without changing centrally assigned tags, expected-service declarations, or other reported endpoints. No new traffic events are generated by the ticker. The ticker runs only in `--demo` mode; each seeded host is labeled `synthetic: true`. Use the reviewed Settings demo-cleanup flow to inspect proven fixture counts, preserve mixed/manual records and create a verified pre-clear backup; do not delete a populated data directory as a routine cleanup procedure.

## TLS and enrollment

```sh
python3 -m controller --init-ca --data-dir .local/secure
```

This creates a development CA and a controller certificate covering `localhost`, `127.0.0.1`, and `::1`. For a remote controller, supply a certificate with the real controller DNS name and an appropriately managed CA. The local development CA key is not a production CA solution.

Installed controllers support Local accounts and SSO through Entra OIDC or SAML, with the same three application roles. On a fresh empty account database, local `admin` / `admin` receives Super Admin and must change its password before workspace access. It is seeded once and never recreated on restart. This built-in account cannot be deleted, disabled, renamed, demoted or have its profile edited; password change/reset and session revocation remain available. Existing Entra estates retain their users without receiving default credentials. Use [the GUI login procedure](../docs/local-and-saml-login.md) for local users, password changes/resets and SAML metadata configuration, and **Settings → Setup** for verified Entra configuration. No manual `.env` editing or token-file retrieval is needed for normal installed setup. The commands below describe local development; explicitly enabled shared role tokens remain directory-unconfigured lab compatibility mechanisms and cannot authorize live production enforcement.

```sh
python3 -m controller --listen 127.0.0.1:8787 --data-dir .local/secure \
  --cert .local/secure/pki/controller.pem --key .local/secure/pki/controller-key.pem \
  --ca .local/secure/pki/ca.pem --ca-key .local/secure/pki/ca-key.pem
```

The browser uses a local-password, Entra OIDC or SAML-authenticated cookie session; endpoint report/policy/flow routes separately require a verified enrolled client certificate. Enrollment alone uses a 15-minute, single-host token issued by an admin through `POST /api/v1/enrollment-tokens`. Enrollment is identity-only. New token requests reject nonempty `tags` or location fields; stored defaults on legacy tokens are ignored. Endpoint-supplied business tags/location cannot assign policy metadata. Administrators manage business metadata centrally in the dashboard. Retrying the same token, CSR and hostname within its original expiry returns the original server ID and certificate response, so a lost network response does not create a duplicate endpoint. A different CSR or hostname, an expired replay, or a legacy used token without a cached response is rejected. The controller persists the token hash, CSR digest and public certificate response, never the agent private key. The agent sends a CSR; issuance overrides its subject with the assigned server UUID and issues a 90-day client-auth certificate. A supplied endpoint header or JSON `server_id` cannot replace mTLS identity outside demo mode. Endpoint leaves support authenticated renewal in the 30-day window, tracked 24-hour overlap, registry revocation and separate one-time fresh-key recovery. When the web server and endpoint issuers differ, agents preinstall `endpoint_ca_cert` separately from `ca_cert`; response material cannot replace existing pins. Compiled Go-client loopback same-CA and separate-issuer fixtures passed renewal/revocation/two recoveries, but a live tenant or deployment CA is separate acceptance. Do not treat the development issuer as fleet PKI.

## Optional shared PostgreSQL HA

Install the optional driver in your environment:

```sh
python3 -m pip install -r controller/requirements.txt
```

Set `SEG_DATABASE_URL` and `SEG_TRAFFIC_DATABASE_URL` through a secret manager or protected environment file. They identify the deployment's shared, writable PostgreSQL metadata and traffic databases. All controller nodes must use the same two shared stores; DSNs are never returned by status APIs. This direct external-DSN compatibility path does not migrate local SQLite automatically. The default same-appliance installer/GUI provides an explicit supervised reviewed migration/join path; see [the HA runbook](../docs/ha.md).

Start each node with its own identity/site and the deployment's TLS/CA configuration:

```sh
python3 -m controller --ha --controller-id dc1-controller-1 --site dc1 \
  --listen 0.0.0.0:8787 --cert /etc/prthak/controller.pem \
  --key /etc/prthak/controller-key.pem --ca /etc/prthak/ca.pem \
  --ca-key /etc/prthak/ca-key.pem
```

`SEG_CONTROLLER_ID` and `SEG_CONTROLLER_SITE` provide the same identity/site defaults. `SEG_SITE` is a backward-compatible site alias; `SEG_CONTROLLER_SITE` wins when both are set. Each node requires identical configured Entra registration/secret/redirect values and enrollment trust. Shared metadata includes local/SSO users, salted local-password hashes, SAML configuration, hashed sessions and one-use login states; callbacks and session requests may reach any ready node. `--ha` refuses synthetic demo mode or missing either database DSN. Supplying database DSNs without `--ha` is also rejected, preventing an accidental SQLite fallback. PostgreSQL connection failures never switch to local state.

- `/healthz` is public process liveness and remains independent of storage.
- `/readyz` is public load-balancer readiness: HTTP 200 only when both writable shared databases and their schema are reachable, otherwise HTTP 503 with dependency booleans. It exposes no DSNs or driver error text.
- Authenticated `/api/v1/cluster` lists controller IDs/sites/readiness and the storage mode. HA nodes record a shared heartbeat every 10 seconds; a node becomes offline after 30 seconds without one. SQLite mode reports a single standalone node.
- Metadata JSON read/modify/write operations hold a PostgreSQL advisory transaction lock through commit or rollback. Traffic has a distinct lock/database. Queue processing inserts deduplicated events and marks each batch processed in the same transaction.
- Background health and traffic jobs use PostgreSQL advisory session leadership locks held across the entire callback. Session loss releases leadership; transaction locks and idempotent writes protect the work during takeover. A node failure can therefore be handled by another controller using the same stores.

The adapter supports multiple active controller frontends. The default appliance also provides managed three-copy PostgreSQL 16/Patroni/etcd setup, reviewed joining, replication/internal-leaf rotation, database backup schedules and supervised recovery with two explicit confirmations by the same current Super Admin. Redundant external ingress, native watchdog reset/fencing, physical WAN/site behavior and measured RPO/RTO remain infrastructure acceptance. The direct `--ha` compatibility path alone does not transform an arbitrary standalone database into HA. The load balancer must preserve endpoint TLS client-certificate identity. Use identical application versions and managed trust/issuance material across nodes.

## Behavior

- Saved groups support arbitrary tag-based membership (`type: "dynamic"`, nonempty `selector`) and explicit enrolled-host membership (`type: "static"`, `server_ids`). Dynamic selectors AND their key/value conditions. Static groups may be empty and then match no hosts. `GET /api/v1/groups` returns current `member_ids` and `member_count`; group CRUD is Admin/Super Admin only.
- A policy can target either `group_ids` or a tag `selector`. Multiple saved groups form a union. With nonempty `group_ids`, `selector` must be `{}`. Unknown group references are rejected; a missing group never falls back to an all-host match. A referenced group cannot be deleted until policies stop referencing it. With empty `group_ids`, existing tag targeting (including an explicitly empty, all-host selector) remains supported.
- Dynamic group membership and intended policy assignments update when central tags/location change, a discovered address matches a central CSV/subnet assignment, or groups are edited. Renaming a group or changing irrelevant labels does not bump unchanged per-host policy versions. Enrollment and metadata assignment alone do not enable enforcement: a changed effective bundle requires its own managed rollout approvals.
- Tag-based source resolution uses enrolled endpoint addresses and centrally assigned business labels. Admin and Super Admin can change tags/location and expected-service declarations; Read Only is view-only. Agents cannot assign policy labels, and enrollment tokens contain no business metadata. CIDRs and source selectors form a union.
- Source lists are sorted and hashed. A host's access version changes only when its effective service rules change. A source group membership or IP change can therefore update other hosts.
- Each compiled service has a `mode`, so monitored service sources cannot widen enforced services. If an enforced service and a monitored service overlap on the same port, the enforced service's source union controls access.
- Learning assignments and five-minute stop/expiry tombstones are included in the response ETag separately from the access-policy digest. Starting/stopping learning changes what the agent fetches without rewriting access policy versions. Active assignments remain in `learning_sessions`; `learning_tombstones` includes `stopped_at` so the endpoint can drain only observations from before the effective cutoff.
- `collector_status` is the endpoint's last reported state. `collector_desired_status` records the controller request; `learning_stop_pending` remains true until the endpoint reports collection stopped. Offline endpoints expose `collector_state: "unknown"` and `collector_status_stale: true` rather than claiming cleanup succeeded. The synthetic demo ticker may simulate an immediate acknowledgement.
- A health evaluator runs every 30 seconds, independent of API traffic. It expires learning, detects stale heartbeats after `max(180, 3 × control_interval_seconds)` seconds, detects missing expected listeners and policy errors, and resolves recoveries. Service discovery defaults to a separate 900-second interval. `discovery_performed: false` heartbeats never refresh `last_discovery_at`, replace listener metadata, or generate discovery events. A fresh successful scan records actual protocol, port, bind address, process, service, application, systemd unit and PID; service labels come from endpoint metadata, not port-number guesses. `discovered_at` timestamps are retained and `next_discovery_at` is the expected next scan time, subject to agent scheduling.
- Listener identity is protocol/port/address. `first_seen` stays stable, `last_seen` advances only on successful scans, and `is_new` highlights additions/changed service metadata until the related alert is acknowledged or 24 hours passes. Initial inventory generates informational `service_discovered` events; later additions and service changes generate warning events. PID-only process restarts do not generate new-service alerts. `discovery_changes` records new/changed/removed listeners from the latest successful scan; cached reports preserve it.
- A vanished listener is reported only from fresh successful inventory. Failed or overdue discovery preserves last-known listener data, exposes `discovery_status` as error/stale/unknown, and sets service health unknown instead of inventing a service outage. Expected-service checks use inventory only while it remains within its reported discovery interval; heartbeat offline detection remains independent.
- The traffic upload returns 202 only after a durable SQLite enqueue in a separate database. A separate worker imports batches idempotently. Flow storage does not share an inventory database or lock. Expired/stopped sessions accept events timestamped inside their actual learning window for a five-minute upload grace, then return 410. Wrong-endpoint uploads return 403. Payload validation failures return 400.
- Traffic retention defaults to 24 hours. Session metadata and audit remain. Counts describe observed events, not verified successful connections. The API returns at most 500 aggregate rows per query; overview totals based on those rows are bounded summaries, not accounting totals for an unlimited fleet.
- Learning coverage includes reported start/end, dropped events, rate-limited status and collection errors. Collection is optional and temporary; inventory and policy delivery continue afterward.
- Local/SSO session writes are audited by their individual provider/account actor. Exactly three roles apply: Read Only views; Admin manages infrastructure; Super Admin also exclusively creates/manages all application users. Ordinary changes use one Admin; explicit restrictive confirmations are by the same actor.

## Central metadata management

The dashboard/API is the business-metadata authority. Each server has one saved DC/cloud location and multiple custom tags. Create the location catalogue entry first; renaming its name/geography preserves its immutable ID and policy/group bindings. Agent-discovered listener application/process names are inventory, not business application tags.

Administrators can edit an individual server or select explicit server IDs for bulk assignment. Bulk merge updates only specified keys; remove records a persistent manual removal, and reset returns that key to automatic. Location edits can pin a saved location or explicit Unassigned; only Return to automatic clears that manual pin. Existing nonempty assignments migrate as manual overrides. Assignment sources and conflicts are visible on the endpoint.

CSV import uses exact-IP profiles for current or future endpoints, with a complete validated preview followed by a separate nonce-bound apply. The template is `ip,application,dc,network_zone,criticality,tag.owner`; additional custom tag columns use `tag.key`. Blank cells retain previous profile values, and manual choices remain effective. Unknown locations, duplicate/ambiguous addresses and invalid rows block the import. The CSV dialog's profile manager lists current/future bindings with pagination and removes obsolete profiles through a reviewed deletion plan. Removing a profile preserves manual overrides and recalculates remaining CSV/subnet/default values.

Subnet mappings bind a CIDR to an existing saved location and apply to current eligible servers and future discoveries. The longest matching prefix wins per address; different DC results across a server's addresses are reported as a conflict instead of choosing a DC. Effective precedence is **manual override → exact-IP CSV profile → subnet location → unassigned**. Subnets supply no tags; tags without a manual/CSV value are absent.

Bulk, CSV and subnet plans show before/after assignments, expire, and reject apply if relevant reviewed state changes. They persist in the shared inventory store for HA. These operations update dynamic membership and compile intended policy versions. Eligible ordinary hosts inherit the saved current Admin-authorized symbolic intent. Changed whole-server default-deny bundles require a fresh dedicated downtime acknowledgement. See [the API contract](../docs/api-contract.md) for request schemas and limits.

## Imported firewall review and optional security observations

`GET /api/v1/firewall` imports exact runtime/permanent entries and groups common rules by zone/kind/value. Fingerprints and snapshot digests are recomputed from the actual rule text. Unsupported targets, bindings, direct rules, service definitions and policy objects remain view-only. Named-service transports come from endpoint-resolved service definitions; custom SSH on 2022 is never guessed to be port 22. Partial/error collection retains last-known inventory and blocks new edits.

Admins can draft bulk changes at `/api/v1/firewall/changes`. A draft binds explicit endpoint IDs, exact old entries/scopes, snapshot and target digests, before/after transport metadata, impact and unmatched hosts. Review expires after ten minutes and inventory/tag drift invalidates it. Confirmation uses a fresh one-time nonce per step. Access removal/replacement, existing denies, new denies or unknown restrictive effects require a second request with a plan-bound typed phrase; client-supplied counts cannot skip either step. Fully confirmed operations remain deliverable for 24 hours, separately from compiled access-policy versions. An endpoint must also opt in locally and verify its own snapshot/management protection. Reported applied/failed/conflict/preview outcomes are bound to that endpoint and plan digest. Cancelling delivery does not reverse any operation already executing or applied.

Closed-port security monitoring is a separate local opt-in. Endpoint reports carry bounded observations and capture-time listener checks, plus coverage/error/rate-limit/drop metadata. The controller durably processes and acknowledges exact stable event IDs in the same metadata transaction, retaining deduplication receipts for 24 hours. Known listeners can suppress a hit only when the cached successful scan is at least as fresh as the event's direct check. Historical observations attested as collected while monitoring can drain after monitoring is disabled. Unknown/stale checks and nonlocal destinations do not produce probe alerts. One-hour source/host/port alert aggregation uses indexed pointers rather than scanning alert history. Five distinct ports within five minutes of observation time can raise `possible_scan`; these observations never establish confirmed lateral movement or compromise and never auto-block sources. Synthetic demo inventory is explicitly marked for review; it does not fabricate security packets or apply-result acknowledgements.

## Scale and deployment boundary

This is a runnable lab development release, not a control plane certified for 5,000 servers. SQLite WAL supplies local storage; activated PostgreSQL shares metadata, membership and the bounded durable traffic queue across controllers. The installed serving path uses bounded Gunicorn HTTPS workers; the development HTTP compatibility handler remains for selected local/fixture paths. Current local or SSO Admin authority, signed assignments/releases, certificate lifecycle, reviewed Slack/email/webhook delivery, backups and supervised recovery are implemented with isolated evidence. Before deployment, complete the intended live Entra/SAML/MFA and provider integrations, native OS/firewall and database-host watchdog/fencing tests, real network/site-failure drills and fleet/flow resource/soak sizing. Virtual-identity/private-process tests do not establish those results, and the 20-server pilot has not started.


## Current authority and operator workflows

An authorized local or SSO Admin publishes ordinary managed changes directly. Restrictive imported changes and learned edits/removal retain explicit confirmations by the same Admin; initial auto-allow requires exact fresh-scope authority. Whole-server default deny requires its separate manually checked downtime acknowledgement. Shared-token/demo authority remains explicitly lab-only. Agent 0.14 validates an independently pinned Ed25519 assignment envelope. Optional offline artifacts have no online-key fallback; release archives support separate dedicated signatures verified before extraction.

Super Admin Settings manages reviewed current-node application-port changes, reviewed notifications, endpoint/internal certificate administration and supervised Recovery. Exact queued/blocked/applied states and endpoint/runtime receipts remain separate. Notifications default off; private TLS webhook/SMTP fixtures do not prove a real provider. Recovery preserves current protected safety context, drains writers, retains originals and requires fresh sessions/policy review after completion. Missing current trusted context blocks online recovery. See [current pilot operations](../docs/pilot-gui-installation.md) and the [current illustrated guide](../docs/guide/prthak-pilot-0.14.0.pdf).

Application-port review/apply changes only the standalone listener or local appliance publisher, with revision/nonce/digest/typed-phrase/dependency acknowledgement and durable verified outcome/rollback. Range 1–65535 is constrained by actual bind permissions/collisions; no privileges are added. The configured application/SSO origin and external clients/LB/DNS/firewall are preserved. Private CLI/Gunicorn handover, original-argument restart persistence and failed-candidate restoration passed; external ingress and live Entra remain deployment acceptance. Demo preview is permitted but applying is blocked.
